# 커버리지(Coverage) 기본 개념

검증(verification) 과정에서 "테스트를 얼마나 충분히 돌렸는가"를 정량적으로 재는 지표가 커버리지다. 시뮬레이션이 통과했다는 것과, 설계의 동작을 빠짐없이 확인했다는 것은 다른 문제이며 커버리지는 그 간극을 보여준다.

## 1. 코드 커버리지 vs 기능 커버리지

커버리지는 크게 두 갈래로 나뉜다.

- **코드 커버리지 (Code Coverage)**: RTL 코드 자체를 얼마나 실행/토글시켰는지를 기계적으로 측정. 도구가 자동으로 계측하므로 별도 작성 없이 켜기만 하면 된다.
- **기능 커버리지 (Functional Coverage)**: 검증 엔지니어가 "이 기능이 이 조건에서 확인됐는가"를 직접 정의(SystemVerilog의 `covergroup` / `coverpoint` / `cross`)해서 측정. 설계 의도와 스펙을 반영하므로 자동으로는 나오지 않는다.

코드 커버리지가 100%여도 기능 커버리지는 낮을 수 있다(코드는 다 실행됐지만 의미 있는 시나리오는 안 돌렸을 수 있음). 반대로 기능 커버리지 위주로만 보면 미처 예상 못 한 코드 경로를 놓칠 수 있다. 실무에서는 둘을 같이 본다.

## 2. 코드 커버리지의 세부 종류

| 종류 | VCS `-cm` 옵션 | 무엇을 재는가 |
| --- | --- | --- |
| Line/Statement | `line` | 각 코드 라인이 최소 1번 이상 실행됐는가 |
| Toggle | `tgl` | 각 신호(bit)가 0→1, 1→0으로 실제로 전이됐는가 |
| Condition/Expression | `cond` | `if`, `&&`, `||` 등 조건식의 각 부분식이 true/false를 모두 가져봤는가 |
| Branch | `branch` | `if/else`, `case`의 각 분기가 모두 실행됐는가 |
| FSM | `fsm` | 상태 머신의 모든 상태와 상태 전이(transition)가 발생했는가 |
| Assertion | `assert` | SVA(SystemVerilog Assertion)가 얼마나 커버/실패했는가 |

여러 개를 동시에 켤 수도 있다 (예: `-cm line+cond+tgl+fsm`).

## 3. Toggle Coverage가 왜 왜곡되기 쉬운가

Toggle coverage는 "신호 비트가 몇 % 전이했는가"를 재는데, 다음과 같은 신호는 원래 잘 안 바뀌는 게 정상이라 수치를 깎아먹는다.

- 테스트벤치 내부용 상수/식별자 (예: 케이스 이름 문자열)
- 리셋 이후 고정되는 설정 레지스터
- 사용하지 않는 상위 비트(예: 32비트 버스인데 실제로는 8비트만 씀)

그래서 toggle coverage는 "DUT(Design Under Test) 로직만" 대상으로 좁혀서 봐야 의미가 있고, 테스트벤치 전용 변수는 제외(exclusion) 처리하는 게 일반적이다. 구체적인 제외 절차(Verdi Exclusion Manager, `.el` 파일)는 [journal/2026-09-22.md](../journal/2026-09-22.md) 참고.

## 4. 커버리지 목표를 100%로 안 잡는 이유

- **도달 불가능한 코드**: 방어적으로 짜놓은 `default` 분기, 이론상 불가능한 상태 조합 등은 실제로 절대 실행되지 않는다.
- **의미 없는 신호**: 위 3번처럼 테스트벤치 전용 변수나 사용하지 않는 비트는 애초에 토글될 이유가 없다.
- **비용 대비 효율**: 마지막 몇 %를 채우기 위한 테스트 케이스 작성 비용이 실제로 잡을 수 있는 버그 대비 너무 커지는 지점이 있다.

그래서 실무에서는 100% 자체보다 "왜 이 %가 안 채워졌는지 설명 가능한가"를 더 중요하게 본다. 채워지지 않은 부분이 정당한 제외 대상인지, 아니면 실제로 빠진 테스트 케이스인지 구분하는 게 커버리지 분석의 핵심이다.

## 5. 리포트를 볼 때 주의할 점 (VCS `urg` 기준)

`urg`로 만든 `dashboard.html`에는 두 종류의 요약이 같이 나온다.

- **Total Coverage Summary** (인스턴스 기준): 실제로 인스턴스화된 모듈 각각을 개별로 카운트. 검증 판단에 쓰는 값은 이쪽.
- **Total Module Definition Coverage Summary** (모듈 정의 기준): 같은 모듈이 여러 번 인스턴스화돼도 정의 1개로만 카운트. 참고용.

Elfile로 신호를 제외해도 반영되는 건 인스턴스 기준 쪽이므로, 최종 판단은 항상 위쪽 Total Coverage Summary로 한다.
